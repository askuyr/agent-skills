# Репозитории и remote

Проверка доступа, клонирование пачкой, ветки и приватность. Деплой на Pages — скилл `site-ship`.

## 1. Проверка доступа

```powershell
gh auth status                     # GitHub: какой аккаунт, какие scopes
git config --global user.name      # подпись коммитов
git remote -v                      # где лежит текущий проект
```

- GitLab: `git ls-remote https://gitlab.com/<group>/<repo>.git` — 200/пусто = доступ есть, запрос пароля/404 = нет.
- Ошибка `could not read Username` / `Permission denied (publickey)` — это доступ, а не код. Не переписывать историю и не менять remote на другой хост без просьбы.
- Токен не печатать в чат и не писать в файлы проекта.

## 2. Скачать все репозитории

1. Список: `gh repo list <user> --limit 200 --json name,isPrivate,defaultBranchRef`.
2. Клонировать в `%USERPROFILE%\Documents\GitHub\<name>`, имя папки = имя репозитория. Уже существующую папку не перезаписывать: `git -C <path> fetch` и показать расхождение.
3. Не тянуть архивы и бинарники без нужды; крупные репозитории — `--depth 1`.
4. Итоговая таблица: репозиторий → локальный путь → ветка → есть ли незакоммиченные правки.

Проекты в OpenCode добавляются вручную (TUI) или через конфиг; папки проектов менять не нужно — скилл `opencode-config`.

## 3. Ветки перед редизайном

Пользователь просит «отдельную и бекап ветку» — делать обе:

```powershell
git branch backup-<дата>          # снимок текущего состояния
git switch -c redesign/<тема>     # рабочая ветка
```

- Работать только в рабочей ветке, `main` не трогать до приёмки.
- Перед экспериментами — `git status`; грязное дерево не тащить в бекап-ветку молча.
- Возврат: `git switch main` после подтверждения; при «откати» — `git reset --hard backup-<дата>` только для своей ветки.

## 4. Приватность и Pages

- GitHub Pages для приватного репозитория работает только на платном плане. Если просят «скрытый репозиторий, но чтобы открывался» — честно сказать про план и предложить: публичный репозиторий с пометкой «шуточный/демо» либо хостинг с приватным доступом.
- Секреты, ключи, `.env` — в `.gitignore` до первого коммита. Уже закоммиченный ключ считается утёкшим.
- `CNAME`, DNS и индексация — в `site-ship`, не дублировать.

## Жёсткие правила

- Не делать force-push в чужие ветки и не переписывать историю без явной просьбы.
- Не «оптимизировать» структуру папок пользователя: раскладка `Documents\GitHub\<repo>` — норма.
- Отчёт: что проверено, что склонировано, какие ветки созданы, что требует действий пользователя (вход, токен, план).
